01

O que é — e o que não é

O scanner de verdade mora em outro repositório. Aqui está só a configuração de CI que o invoca, versionada e publicada como se fosse um pacote.

O scanner é uma imagem Docker publicada a partir de Tooark/base-images como ghcr.io/tooark/security-scanner:1.9. Dentro dela existe um CLI chamado ark-tools, que orquestra três ferramentas e produz um relatório JSON no formato ark-report-tools v1.2.

Este repositório resolve um problema diferente e bem específico:

O problema

“Temos 40 projetos. Não quero copiar 80 linhas de YAML de segurança em cada um deles, e quando o scanner mudar não quero editar 40 arquivos.”

Em vocabulário de desenvolvimento: este repositório é uma biblioteca, e os projetos que a consomem são os dependentes. A tag v1.0.0 é a versão do pacote. Quem consome não copia código — declara uma dependência.

Duas fachadas sobre o mesmo comportamento

O complicador é que a empresa usa GitHub Actions e GitLab CI, que são sistemas incompatíveis. Então a mesma biblioteca é publicada com dois front ends:

PlataformaFormatoArquivos
GitHub Composite Action action.yml + src/run-scanner.sh
GitLab CI/CD Components templates/ — 7 arquivos, um por scan

A regra que o projeto se impõe: mesmos nomes de input, mesmos defaults e mesma precedência nas duas plataformas — só a sintaxe muda (kebab-case no GitHub, snake_case no GitLab). Metade dos scripts em scripts/ existe só para impedir que essa paridade se perca com o tempo.

What it is — and what it is not

The scanner itself lives in another repository. What is here is only the CI configuration that invokes it, versioned and published as if it were a package.

The scanner is a Docker image built from Tooark/base-images and published as ghcr.io/tooark/security-scanner:1.9. Inside it there is a CLI called ark-tools that orchestrates three tools and produces a JSON report in the ark-report-tools v1.2 format.

This repository solves a different and very specific problem:

The problem

“We have 40 projects. I do not want to copy 80 lines of security YAML into each of them, and when the scanner changes I do not want to edit 40 files.”

In development vocabulary: this repository is a library, and the projects that consume it are its dependents. The tag v1.0.0 is the package version. Consumers do not copy code — they declare a dependency.

Two front ends over the same behaviour

The complication is that the company uses GitHub Actions and GitLab CI, which are incompatible systems. So the same library is published with two front ends:

PlatformFormatFiles
GitHub Composite Action action.yml + src/run-scanner.sh
GitLab CI/CD Components templates/ — 7 files, one per scan

The rule the project imposes on itself: same input names, same defaults and same precedence on both platforms — only the syntax differs (kebab-case on GitHub, snake_case on GitLab). Half of what lives in scripts/ exists only to stop that parity from eroding over time.

Os conceitos de CI, em termos de dev

Cinco termos destravam a leitura de qualquer arquivo deste repositório.

TermoO que éAnalogia
Pipeline
/ Workflow		 Tudo que roda quando você dá push A main() do build
Job Unidade isolada de trabalho, em um container ou VM limpa Uma função — roda em processo próprio
Stage Agrupamento sequencial de jobs (build → test → deploy) Fases. Jobs no mesmo stage rodam em paralelo
Runner A máquina que executa o job O servidor onde o processo roda
Artifact Arquivo que o job produz e que sobrevive ao fim dele Valor de retorno persistido

Dois detalhes explicam grande parte do código deste repositório.

Um job começa do zero toda vez

Container novo, disco vazio. É por isso que existe cache — sem ele, o Trivy baixaria um banco de vulnerabilidades de centenas de megabytes a cada execução. O cache é o assunto de boa parte do action.yml.

Um job “falha” quando o comando sai com exit code diferente de zero

É assim que um scanner bloqueia um merge: ele encontra uma CVE crítica e retorna 1. Isso se chama failure gate, e boa parte dos inputs deste projeto existe só para você escolher quando o portão fecha.

Trivy

Falha quando uma severidade listada em trivy_severity_fail tem correção disponível.

desligar → trivy_exit_code: "0"

Hadolint

Falha a partir do nível definido em hadolint_failure_level.

desligar → hadolint_failure_level: "none"

Betterleaks

Falha quando qualquer segredo é detectado.

desligar → betterleaks_fail_on_findings: "false"

No GitHub existe um meio-termo: soft-fail: "true" transforma qualquer gate no output exit-code em vez de derrubar o passo — útil para adotar o scanner em um projeto legado sem travar todo mundo no primeiro dia.

CI concepts, in dev terms

Five terms unlock reading any file in this repository.

TermWhat it isAnalogy
Pipeline
/ Workflow		 Everything that runs when you push The build's main()
Job An isolated unit of work, in a fresh container or VM A function — runs in its own process
Stage A sequential grouping of jobs (build → test → deploy) Phases. Jobs in the same stage run in parallel
Runner The machine that executes the job The server the process runs on
Artifact A file the job produces that outlives it A persisted return value

Two details explain much of the code in this repository.

A job starts from nothing every time

New container, empty disk. That is why caching exists — without it Trivy would download a vulnerability database of hundreds of megabytes on every run. The cache is the subject of a good part of action.yml.

A job “fails” when the command exits non-zero

That is how a scanner blocks a merge: it finds a critical CVE and returns 1. This is called a failure gate, and much of this project's input surface exists only so you can choose when the gate closes.

Trivy

Fails when a severity listed in trivy_severity_fail has a fix available.

turn off → trivy_exit_code: "0"

Hadolint

Fails at or above the level set in hadolint_failure_level.

turn off → hadolint_failure_level: "none"

Betterleaks

Fails when any secret is detected.

turn off → betterleaks_fail_on_findings: "false"

On GitHub there is a middle ground: soft-fail: "true" turns any gate into the exit-code output instead of failing the step — useful for adopting the scanner in a legacy project without blocking everyone on day one.

05

A fachada GitHub: action.yml

Uma composite Action é uma Action feita de outras Actions e comandos shell, sem código compilado.

Quando alguém escreve uses: Tooark/ci-security-scanner@v1.1.0, o GitHub baixa este repositório e executa os passos declarados aqui dentro do job de quem chamou. O arquivo tem quatro blocos.

inputs: — os parâmetros

São cerca de 45, cada um com description e default. Pense neles como a assinatura de função pública da biblioteca: é o contrato com quem consome, e mudá-los quebra gente. 

trivy-severity:
  description: "Severities included in the report, e.g. CRITICAL,HIGH."
  required: false
  default: ""

Quase todos têm default: "". Isso não é preguiça — é a regra de precedência, explicada em Decisões.

outputs: — o retorno

exit-code, reports-dir e report. Permite que o passo seguinte leia o resultado com steps.scan.outputs.exit-code.

branding:

Ícone e cor no GitHub Marketplace. Puramente cosmético.

runs: — o corpo da função

Quatro passos, nesta ordem:

  1. cache — calcula em bash se o cache do Trivy deve ser usado e com qual chave. dockerfile-lint e secret-scan pulam, porque Hadolint e Betterleaks nunca leem o banco de CVEs.
  2. Restore the Trivy database — actions/cache/restore@v4.
  3. scan — chama bash "$GITHUB_ACTION_PATH/src/run-scanner.sh". É aqui que o trabalho acontece. Todo o resto é entrada e saída.
  4. Save the Trivy database e Upload security reports — salvam o cache e publicam os relatórios como artifact.

O detalhe que vale internalizar

No bloco env: do passo scan:

env:
  ARK_IN_TRIVY_SEVERITY: ${{ inputs.trivy-severity }}
  ARK_IN_IMAGE:          ${{ inputs.image }}

Os inputs não são interpolados dentro do texto do script. Eles chegam como variáveis de ambiente com prefixo ARK_IN_.

Por quê

Se um input fosse colado direto no corpo do script — run: docker run ... ${{ inputs.image }} — um valor como "; rm -rf / # viraria comando. Passando por env:, ele é sempre apenas um valor. É o mesmo raciocínio de prepared statements contra SQL injection, e é uma classe de bug real e frequente em GitHub Actions.

The GitHub front end: action.yml

A composite Action is an Action made of other Actions and shell commands, with no compiled code.

When someone writes uses: Tooark/ci-security-scanner@v1.1.0, GitHub downloads this repository and runs the steps declared here inside the caller's job. The file has four blocks.

inputs: — the parameters

About 45 of them, each with a description and a default. Think of them as the library's public function signature: it is the contract with consumers, and changing it breaks people. 

trivy-severity:
  description: "Severities included in the report, e.g. CRITICAL,HIGH."
  required: false
  default: ""

Almost all of them are default: "". That is not laziness — it is the precedence rule, explained under Decisions.

outputs: — the return value

exit-code, reports-dir and report. They let the next step read the result with steps.scan.outputs.exit-code.

branding:

Icon and colour on the GitHub Marketplace. Purely cosmetic.

runs: — the function body

Four steps, in this order:

  1. cache — works out in bash whether the Trivy cache should be used and under which key. dockerfile-lint and secret-scan skip it, because Hadolint and Betterleaks never read the CVE database.
  2. Restore the Trivy database — actions/cache/restore@v6.
  3. scan — calls bash "$GITHUB_ACTION_PATH/src/run-scanner.sh". This is where the work happens. Everything else is input and output.
  4. Save the Trivy database and Upload security reports — save the cache and publish the reports as an artifact.

The detail worth internalising

In the env: block of the scan step:

env:
  ARK_IN_TRIVY_SEVERITY: ${{ inputs.trivy-severity }}
  ARK_IN_IMAGE:          ${{ inputs.image }}

Inputs are not interpolated into the text of the script. They arrive as environment variables prefixed with ARK_IN_.

Why

If an input were pasted straight into the script body — run: docker run ... ${{ inputs.image }} — a value like "; rm -rf / # would become a command. Passing through env:, it is always just a value. It is the same reasoning as prepared statements against SQL injection, and it is a real, frequent class of bug in GitHub Actions.

06

A fachada GitLab: templates/

Um CI/CD Component do GitLab é um arquivo YAML com duas metades separadas por ---. 

# metade de cima: declaração de parâmetros
spec:
  inputs:
    trivy_severity:
      default: ""
      regex: "^[A-Z,]*$"      # o GitLab valida antes de rodar
      description: "..."
---
# metade de baixo: o template do job gerado
"$[[ inputs.job_name ]]":
  stage: $[[ inputs.stage ]]
  image: ...
  script: ...

A sintaxe $[[ inputs.x ]] é substituída pelo GitLab no momento em que o pipeline é montado — antes de qualquer coisa rodar.

O spec: do GitLab é mais expressivo que o inputs: do GitHub: aceita options: (enum), regex: e type:. O projeto usa isso — trivy_exit_code só aceita "", "0" ou "1". Quem passa outra coisa recebe erro antes do pipeline rodar, não no meio dele.

Como se consome

# no .gitlab-ci.yml do projeto que quer ser escaneado
include:
  - remote: "https://raw.githubusercontent.com/Tooark/ci-security-scanner/v1.1.0/templates/full-scan.yml"
    inputs:
      stage: security
      image: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
      trivy_severity: "CRITICAL,HIGH"

E aparece no pipeline um job chamado security:full-scan. Como é um job comum, dá para sobrescrever o que os inputs não cobrem apenas redeclarando o nome dele: 

"security:full-scan":
  needs: ["build"]
  cache: []                # desliga o cache do Trivy
  variables:
    TRIVY_SCANNERS: "vuln,secret,misconfig,license"

examples/gitlab/remote-include.gitlab-ci.yml — a “escotilha de escape” do design.

Por que 7 arquivos quase idênticos

Porque no GitLab um template equivale a um job gerado. Não existe um arquivo que gere “o job que você escolher”. A duplicação é imposta pela plataforma — e é exatamente por isso que existe o check-sync.sh: duplicação sem verificação automática apodrece.

E o catálogo?

O CI/CD Catalog do GitLab só lista componentes hospedados na própria instância, então um repositório no GitHub não pode ser publicado nele diretamente. A pasta examples/gitlab-catalog-mirror/ traz o pipeline de um projeto-espelho que fecha essa lacuna: ele consulta os releases do GitHub em um agendamento semanal, copia templates/ quando a versão muda, empurra a tag e publica no catálogo interno. O GitHub continua sendo a fonte da verdade; nada é escrito no espelho.

The GitLab front end: templates/

A GitLab CI/CD Component is a YAML file with two halves separated by ---. 

# top half: parameter declaration
spec:
  inputs:
    trivy_severity:
      default: ""
      regex: "^[A-Z,]*$"      # GitLab validates before anything runs
      description: "..."
---
# bottom half: the template of the generated job
"$[[ inputs.job_name ]]":
  stage: $[[ inputs.stage ]]
  image: ...
  script: ...

The $[[ inputs.x ]] syntax is substituted by GitLab at the moment the pipeline is assembled — before anything runs.

GitLab's spec: is more expressive than GitHub's inputs:: it accepts options: (an enum), regex: and type:. The project uses that — trivy_exit_code only accepts "", "0" or "1". Anyone passing something else gets an error before the pipeline runs, not halfway through it.

How it is consumed

# in the .gitlab-ci.yml of the project to be scanned
include:
  - remote: "https://raw.githubusercontent.com/Tooark/ci-security-scanner/v1.1.0/templates/full-scan.yml"
    inputs:
      stage: security
      image: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
      trivy_severity: "CRITICAL,HIGH"

A job named security:full-scan then appears in the pipeline. Since it is an ordinary job, anything the inputs do not cover can be overridden by redeclaring its name: 

"security:full-scan":
  needs: ["build"]
  cache: []                # disable the Trivy cache
  variables:
    TRIVY_SCANNERS: "vuln,secret,misconfig,license"

examples/gitlab/remote-include.gitlab-ci.yml — the design's escape hatch.

Why 7 nearly identical files

Because on GitLab one template equals one generated job. There is no file that generates “whichever job you pick”. The duplication is imposed by the platform — and that is exactly why check-sync.sh exists: duplication without automated verification rots.

What about the catalog?

GitLab's CI/CD Catalog only lists components hosted on the instance itself, so a GitHub repository cannot be published to it directly. The examples/gitlab-catalog-mirror/ folder carries the pipeline for a mirror project that closes the gap: it polls GitHub releases on a weekly schedule, copies templates/ across when the version moves, pushes the tag and publishes to the internal catalog. GitHub stays the source of truth; nothing is authored in the mirror.

07

O motor: src/run-scanner.sh

246 linhas de bash que traduzem ~40 variáveis ARK_IN_* em um docker run. Quase todo comentário nele documenta um bug que alguém já sofreu.

O caminho completo de uma execução

No GitLab, os passos 2 e 3 não existem: o job é o container, e o template faz o mesmo trabalho em before_script.

O que o script faz, em ordem

Valida o comando contra uma lista fixa de sete. Nenhum input vira comando arbitrário.

Monta os volumes — o workspace vai para /workspace, os relatórios para /reports, o cache do Trivy para /home/app/.cache/trivy.

Reescreve caminhos. Quem escreve path: src/ está falando do disco do runner, mas o container enxerga /workspace/src. A função to_container_path faz essa tradução e deixa URLs e caminhos absolutos passarem intactos.

Encaminha só o que não está vazio. Esta é a função de cinco linhas que sustenta a regra de precedência do projeto inteiro:

add_env() {
  local name="$1" value="$2"
  [ -n "$value" ] || return 0     # ← o coração da precedência
  DOCKER_ARGS+=(-e "$name=$value")
}

Segredos vêm do ambiente, nunca de inputs. TRIVY_TOKEN, REPORT_TOKEN, credenciais de registry e afins são lidos do ambiente do job e repassados ao container; o log imprime ***.

Armadilha

Valores de input aparecem na configuração renderizada do pipeline, visível para quem tem acesso de leitura ao projeto. Um token passado como input é um token vazado.

Monta os argumentos por comando. Cada um dos sete tem uma forma diferente. Um exemplo de cuidado com usabilidade: em full-scan, se você não passou imagem nenhuma, o script liga FULL_SCAN_SKIP_IMAGE=true sozinho, em vez de deixar o Trivy falhar tentando escanear uma string vazia.

Devolve a posse dos arquivos. A imagem roda como usuário não-root (uid 1000), que não é o usuário do runner. Sem o chown de volta no fim, o passo de upload de artifact não conseguiria ler os relatórios que o scanner acabou de escrever.

The engine: src/run-scanner.sh

246 lines of bash that translate ~40 ARK_IN_* variables into a docker run. Almost every comment in it documents a bug someone already hit.

The full path of one run

On GitLab steps 2 and 3 do not exist: the job is the container, and the template does the same work in before_script.

What the script does, in order

Validates the command against a fixed list of seven. No input ever becomes an arbitrary command.

Sets up the volumes — the workspace goes to /workspace, the reports to /reports, the Trivy cache to /home/app/.cache/trivy.

Rewrites paths. Someone writing path: src/ means the runner's disk, but the container sees /workspace/src. The to_container_path function does that translation and lets URLs and absolute paths through untouched.

Forwards only what is non-empty. This is the five-line function that holds up the precedence rule of the whole project:

add_env() {
  local name="$1" value="$2"
  [ -n "$value" ] || return 0     # ← the heart of the precedence rule
  DOCKER_ARGS+=(-e "$name=$value")
}

Secrets come from the environment, never from inputs. TRIVY_TOKEN, REPORT_TOKEN, registry credentials and friends are read from the job environment and passed to the container; the log prints ***.

Trap

Input values appear in the rendered pipeline configuration, visible to anyone with read access to the project. A token passed as an input is a leaked token.

Builds the arguments per command. Each of the seven has a different shape. One example of care for usability: in full-scan, if you passed no image at all, the script turns on FULL_SCAN_SKIP_IMAGE=true itself rather than letting Trivy fail trying to scan an empty string.

Hands file ownership back. The image runs as a non-root user (uid 1000), which is not the runner user. Without the chown at the end, the artifact upload step could not read the reports the scanner had just written.

08

Versão única e testes de contrato

A parte que mais ensina, e o padrão mais transferível deste repositório para qualquer outro projeto.

O problema

A mesma versão do scanner aparece em dez lugares: sete templates, o action.yml e dois fallbacks dentro do run-scanner.sh. Atualizar de 1.9 para 2.0 e esquecer um template significa um projeto rodando versão antiga silenciosamente. YAML não tem compilador; ninguém percebe.

A solução

O VERSION é a constante única:

# Single source of truth for versions in this repository.
COMPONENT_VERSION=1.1.0
SCANNER_IMAGE=ghcr.io/tooark/security-scanner
SCANNER_VERSION=1.9

E o scripts/check-sync.sh é o teste de contrato que falha o CI quando algo diverge. Ele verifica três invariantes:

  1. Todo template e o action.yml pinam exatamente a imagem declarada em VERSION.
  2. Em cada template, todo ARK_IN_* declarado é de fato lido, e todo ARK_IN_* lido foi declarado.
  3. Todo ARK_IN_* definido no action.yml é encaminhado pelo run-scanner.sh.
Por quê

Os itens 2 e 3 pegam o bug mais chato deste tipo de projeto: você adiciona um input, documenta, e esquece de conectar uma das pontas. O input existe na documentação, o usuário passa o valor, e nada acontece. Silenciosamente. O script transforma isso em CI vermelho.

O scripts/validate-templates.py faz o equivalente para a estrutura dos templates GitLab: separador --- presente, todo $[[ inputs.x ]] referencia um input declarado, todo input declarado é usado (input morto é mentira na documentação), default está entre as options, e o template define exatamente um job.

O comentário no topo do arquivo dá a melhor justificativa possível: o GitLab só reporta esses erros quando o pipeline é criado — ou seja, no projeto de quem consome, não neste. Tarde demais.

A regra prática

Ao adicionar um input

Toque nos quatro lugares, ou o check-sync.sh vai te avisar: o spec:inputs do template, o bloco variables: do template como ARK_IN_*, o action.yml, e o src/run-scanner.sh.

Para rodar as validações localmente, antes de abrir o PR:

python3 -m pip install pyyaml

python3 scripts/validate-templates.py
./scripts/check-sync.sh
shellcheck -s bash src/run-scanner.sh scripts/check-sync.sh

Single source of truth and contract tests

The part with the most to teach, and the most transferable pattern in this repository.

The problem

The same scanner version appears in ten places: seven templates, action.yml and two fallbacks inside run-scanner.sh. Updating from 1.9 to 2.0 and forgetting one template means a project silently running the old version. YAML has no compiler; nobody notices.

The solution

VERSION is the single constant:

# Single source of truth for versions in this repository.
COMPONENT_VERSION=1.1.0
SCANNER_IMAGE=ghcr.io/tooark/security-scanner
SCANNER_VERSION=1.9

And scripts/check-sync.sh is the contract test that fails CI when anything diverges. It checks four invariants:

  1. Every template and action.yml pins exactly the image declared in VERSION.
  2. In each template, every declared ARK_IN_* is actually read, and every ARK_IN_* read was declared.
  3. Every ARK_IN_* set in action.yml is forwarded by run-scanner.sh.
  4. Every copy-paste reference in the docs and the examples pins COMPONENT_VERSION.
Why

Items 2 and 3 catch the nastiest bug in this kind of project: you add an input, document it, and forget to connect one of the ends. The input exists in the documentation, the user sets the value, and nothing happens. Silently. The script turns that into a red build.

scripts/validate-templates.py does the equivalent for the structure of the GitLab templates: the --- separator is present, every $[[ inputs.x ]] references a declared input, every declared input is used (a dead input is a lie in the documentation), default is among the options, and the template defines exactly one job.

The comment at the top of the file gives the best possible justification: GitLab only reports these errors when a pipeline is created — which is to say, in a consumer's project, not in this one. Far too late.

The practical rule

When adding an input

Touch all four places, or check-sync.sh will tell you: the template's spec:inputs, the template's variables: block as ARK_IN_*, action.yml, and src/run-scanner.sh.

To run the validations locally, before opening the PR:

python3 -m pip install pyyaml

python3 scripts/validate-templates.py
./scripts/check-sync.sh
shellcheck -s bash src/run-scanner.sh scripts/check-sync.sh

O CI do próprio projeto

Uma dobra que confunde no começo: a pasta .github/workflows/ não tem nada a ver com o que o projeto entrega. É o CI deste repositório, como qualquer outro projeto tem.

ci.yml — roda em push e pull request

Job lint: parseia todo YAML do repositório, roda os dois scripts de validação, roda shellcheck (linter de bash) e actionlint (linter de GitHub Actions).

Job self-scan: o projeto escaneia a si mesmo com a própria Action (uses: ./). Isso é dogfooding e funciona como teste de integração — se a Action estiver quebrada, o próprio CI quebra.

Duas linhas valem atenção:

permissions:
  contents: read     # o token do job só lê — menor privilégio
uses: docker://rhysd/actionlint@sha256:b1934ee5...   # pinado por digest
Por quê

Uma tag Docker (:1.7.12) pode ser reapontada pelo dono da imagem a qualquer momento. Um digest SHA-256 é imutável. Como esse container de terceiro roda dentro do CI deste projeto, pinar por digest impede que código não revisado passe a rodar aqui sem nenhum commit.

release.yml — roda ao dar push em uma tag v*.*.*

Revalida tudo, confere se a tag bate com COMPONENT_VERSION — tag v1.0.1 com VERSION=1.0.0 é release recusada —, cria o GitHub Release com notas geradas e move as tags flutuantes.

Abre um PR semanal atualizando as Actions referenciadas. O comentário no arquivo fecha o raciocínio do digest: sem isso, pinar congelaria a dependência em vez de controlá-la. Pinar sem um mecanismo de atualização não é segurança, é dívida.

The project's own CI

A fold that confuses at first: the .github/workflows/ folder has nothing to do with what the project delivers. It is this repository's CI, like any other project has.

ci.yml — runs on push and pull request

Job lint: parses every YAML file in the repository, runs the two validation scripts, runs shellcheck (a bash linter) and actionlint (a GitHub Actions linter).

Job self-scan: the project scans itself with its own Action (uses: ./). That is dogfooding, and it works as an integration test — if the Action is broken, this repository's own CI breaks.

Two lines are worth noticing:

Why

A Docker tag (:1.7.12) can be repointed by the image owner at any moment. A SHA-256 digest is immutable. Since that third-party container runs inside this project's CI, pinning by digest stops unreviewed code from starting to run here without a single commit.

Revalidates everything, checks that the tag agrees with COMPONENT_VERSION — tag v1.0.1 with VERSION=1.0.0 is a refused release — creates the GitHub Release with generated notes, and moves the floating tags.

Decisões e armadilhas

As escolhas que parecem estranhas na primeira leitura, e o motivo de cada uma. Esta seção é a que mais economiza tempo quando algo dá errado.

A regra de precedência — o motivo dos default: ""

input  >  variável de CI / env do job  >  default da imagem

Input vazio nunca é encaminhado. Isso permite que um projeto defina TRIVY_SEVERITY uma vez como variável global e deixe o input em branco em todos os jobs, em vez de repetir. Definindo os dois, o input ganha.

Se o input vazio fosse encaminhado, ele sobrescreveria a variável global com string vazia e quebraria esse padrão. É a diferença entre undefined e "" — e o projeto trata isso explicitamente nas duas plataformas, com add_env() no bash e ark_apply_inputs nos templates.

O cache do Trivy, e o passo de save separado

O banco de CVEs do Trivy é grande. Baixá-lo a cada build é a parte mais lenta do scan e o jeito mais fácil de bater o rate limit do registry. As duas plataformas cacheiam, com estratégias diferentes: o GitLab aponta TRIVY_CACHE_DIR para .cache/trivy dentro do projeto e usa uma chave fixa, compartilhada por todos os branches; o GitHub usa actions/cache com uma entrada por dia por versão do scanner, com fallback para o dia anterior — assim o Trivy atualiza um banco existente em vez de baixar um inteiro.

A sutileza que explica o passo extra

No GitHub, o actions/cache normal salva em um post step, e post steps são pulados quando um passo anterior falhou. Mas esta Action falha por design quando encontra vulnerabilidade. Sem o passo de save separado, só repositórios que não acham nada populariam o cache — justamente os que menos precisam.

Um detalhe operacional para instâncias self-hosted do GitLab: por padrão o cache do runner fica no disco do próprio runner. Com vários runners, um job só acerta o cache se cair no runner que o escreveu. Configurar distributed caching (S3 ou equivalente) no config.toml é o que torna a taxa de acerto consistente.

entrypoint: [""] em todo template GitLab

A imagem tem um entrypoint que executa ark-tools direto. O GitLab Runner mantém o entrypoint da imagem e anexa um shell a ele. Sem limpar, o job morre antes do script rodar.

GIT_DEPTH: "0" / fetch-depth: 0

Por padrão, CI faz shallow clone (só o último commit) porque é mais rápido. Mas o Betterleaks procura segredos no histórico — e o caso clássico é exatamente a chave commitada e “removida” depois.

Falha silenciosa

Com clone raso, o Betterleaks não vê quase nada e não reclama. O job passa verde e você acha que está protegido. Por isso todo template e todo exemplo força profundidade completa.

docker-socket: "true" entrega root no runner

Montar /var/run/docker.sock dá ao container controle total do daemon Docker do host — ele pode subir um container privilegiado e ler a máquina inteira. Vem desligado. Só é necessário para escanear uma imagem construída no mesmo job; imagem já enviada a um registry não precisa. Em runner self-hosted compartilhado, a recomendação é empurrar para o registry e escanear de lá.

Relatórios podem conter os segredos que encontraram

Duas configurações transformam um artifact em vazamento: betterleaks_redact: "0" escreve os segredos detectados em texto claro, e adicionar secret a trivy_scanners coloca os achados do Trivy no relatório. Artifacts são baixáveis por qualquer um com acesso de leitura ao repositório. O default é redação de 100%, e o log imprime apenas regra, arquivo, linha e commit curto — nunca o segredo.

Propriedade de arquivos no runner do GitHub

A imagem roda como uid 1000, que não é o usuário do runner. O script cria o diretório de relatórios com permissão ampla durante o scan, devolve a posse no fim e fecha as permissões de volta; o workspace é declarado como safe directory do git por variável de ambiente. Em runner efêmero isso é irrelevante; em self-hosted com jobs concorrentes, existe uma janela curta em que outro job poderia escrever ali.

Duas pegadinhas menores

  • dockerfile-lint processa um arquivo por job. Para vários, use full-scan com dockerfiles: "a,b,c", ou inclua o template uma vez por arquivo com job_name diferente.
  • O default vazio de tags renderiza como tags: []. O GitLab não permite que um input omita uma palavra-chave, e lista vazia é como se diz “qualquer runner”. Pipelines aceitam; apenas o schema JSON do editor do GitLab reclama.

Decisions and traps

The choices that look strange on a first read, and the reason behind each. This is the section that saves the most time when something goes wrong.

The precedence rule — why default: "" everywhere

input  >  CI variable / job env  >  image default

An empty input is never forwarded. That lets a project set TRIVY_SEVERITY once as a global variable and leave the input blank in every job, instead of repeating it. Set both and the input wins.

If an empty input were forwarded, it would overwrite the global variable with an empty string and break that pattern. It is the difference between undefined and "" — and the project handles it explicitly on both platforms, with add_env() in bash and ark_apply_inputs in the templates.

The Trivy cache, and the separate save step

Trivy's CVE database is large. Downloading it on every build is the slowest part of a scan and the easiest way to hit a registry rate limit. Both platforms cache it, with different strategies: GitLab points TRIVY_CACHE_DIR at .cache/trivy inside the project and uses a fixed key shared by every branch; GitHub uses actions/cache with one entry per day per scanner version, falling back to the previous day — so Trivy refreshes an existing database instead of fetching a whole one.

The subtlety that explains the extra step

On GitHub, the normal actions/cache saves in a post step, and post steps are skipped when an earlier step failed. But this Action fails by design when it finds a vulnerability. Without the separate save step, only repositories that find nothing would ever populate the cache — precisely the ones that need it least.

An operational detail for self-hosted GitLab instances: by default the runner cache lives on the runner's own disk. With several runners, a job only hits the cache if it lands on the runner that wrote it. Configuring distributed caching (S3 or equivalent) in config.toml is what makes the hit rate consistent.

entrypoint: [""] in every GitLab template

The image has an entrypoint that execs ark-tools directly. GitLab Runner keeps the image entrypoint and attaches a shell to it. Without clearing it, the job dies before the script runs.

GIT_DEPTH: "0" / fetch-depth: 0

By default CI does a shallow clone (only the last commit) because it is faster. But Betterleaks looks for secrets in the history — and the classic case is exactly the key that was committed and “removed” afterwards.

Silent failure

With a shallow clone, Betterleaks sees almost nothing and does not complain. The job passes green and you believe you are protected. That is why every template and every example forces full depth.

docker-socket: "true" hands over root on the runner

Mounting /var/run/docker.sock gives the container full control of the host's Docker daemon — it can start a privileged container and read the whole machine. It is off by default. It is only needed to scan an image built in the same job; an image already pushed to a registry does not need it. On a shared self-hosted runner, the recommendation is to push to the registry and scan from there.

Reports can contain the secrets they found

Two settings turn an artifact into a disclosure: betterleaks_redact: "0" writes detected secrets in cleartext, and adding secret to trivy_scanners puts Trivy's findings in the report. Artifacts are downloadable by anyone with read access to the repository. The default is 100% redaction, and the log prints only rule, file, line and short commit — never the secret.

File ownership on the GitHub runner

The image runs as uid 1000, which is not the runner user. The script creates the reports directory with broad permissions during the scan, hands ownership back at the end and tightens the permissions again; the workspace is declared a git safe directory through environment variables. On an ephemeral runner this is immaterial; on a self-hosted one with concurrent jobs there is a short window in which another job could write there.

Two smaller gotchas

  • dockerfile-lint handles one file per job. For several, use full-scan with dockerfiles: "a,b,c", or include the template once per file with a different job_name.
  • The empty default of tags renders as tags: []. GitLab has no way for an input to omit a keyword, and an empty list is how you say “any runner”. Pipelines accept it; only GitLab's editor JSON schema objects.
